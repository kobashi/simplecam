# 発音ノイズ調査

対象: `8a98fc0` 相当の音響処理。未公開のUIマニュアル変更を含む作業ツリーで調査。

## 結論と検証範囲

音量超過だけでなく、ENVの余韻制御、画像の閾値による急変、音響パラメータ更新負荷、FMの折り返しを分けて対処する必要がある。
現時点でユーザーが聞いたノイズそのものの原因は確定していない。

本調査はコード確認、Web Audio仕様確認、実装関数を使った数値再現によるもの。
カメラ、スピーカー、ブラウザの実オーディオ描画、実機のバッファアンダーランは測定していない。
サーバー起動と公開は行っていない。後述の対策を調査後にローカル実装した。

## 適用した対策

- ENVのマスター音量を瞬時輝度から切り離し、発音時の輝度を各ボイスのピークへ反映。
- 無音フレームで再トリガーせず、非アクティブになった音の既存Releaseを維持。
- AudioContextへ`latencyHint: balanced`を指定し、8〜20ms先へAudioParamを予約。
- 通常モードの音響解析上限を30fpsへ変更。
- サンプルレートとキャリア周波数からFM変調量を制限。
- WaveShaperを2倍オーバーサンプリング。
- ページ非表示時に20msフェードしてからAudioContextを休止。

数値診断は、暗転後もENVマスターが輝度で下降しないこと、無音フレームが進行中のReleaseを28msで切らないこと、FM高音域で変調量が制限されることを確認する。
実機のスピーカー歪みとブラウザ・OSのバッファアンダーランは引き続き実測が必要。

再現コマンド:

```sh
node scripts/investigate-audio.mjs
node --test tests/audio-automation.test.mjs tests/audio-trigger.test.mjs
```

診断スクリプトはapp.jsの解析・発音関数とAudioAutomationを使用する。
AudioParamはAPI呼び出しを数えるスタブなので、出力値はJavaScript側の予定値であり、実際にレンダリングされたPCMではない。

## 1. ENVのReleaseより先に音が消える: 数値再現済み

`triggerEnvelopeAudio`は全ボイスへ新しいエンベロープを設定する。
黒フレームでは全音の`active`がfalseになり、各`peakGain`が0になる。
再トリガー時は、それまで鳴っていた音もAttack時間28msで0へランプする。
Releaseを2000msにしてもこの処理は変わらない。

再トリガー待機中にも別経路で余韻が削られる。
`updateAudioFromFrame`はENVのON/OFFにかかわらず現在画像の明るさからマスター音量を更新する。
ENV ONの時定数は50ms。暗転して目標値が0になると、暗転時のマスター値に対し、
50ms後は36.8%、150ms後は4.98%、300ms後は0.248%となる。

これらは数学的な振幅の不連続ではないが、設定したReleaseと異なる短い消音と再アタックを作る。
強い明暗変化で発生するパルス的な音の有力候補。可聴クリックを断定するにはPCMと実音の確認が必要。

対処候補: ENVで発音した音の明るさを保持し、画像から消えた音はRELで終わらせる。
マスターの画像追従と発音ごとの音量を分離する。連続音モードは別に評価する。

## 2. 高コントラストで解析値が急変する: コード・数値で確認

Shaderは閾値未満を完全な黒へ落とし、RGB成分を0〜1へクランプする。
音響解析はその後の映像を使用し、以下の離散判定を行う。

- 黒ピクセルを除外。
- 補正彩度0.12未満を音程判定から除外。
- RGB値を4段階へ分類し、1ピクセルでも存在すると音程候補になる。
- 全領域の最大RGB値をマスター音量の基準にする。

暗部が黒へ落ちたり、明部が白くなったりすると、音程の参加・退出、平均彩度、倍音量が一緒に変わる。
SAT=0の真っ白な画像は、明るさ1でも音程候補0。SAT=100では3音が参加する。

2304画素中1画素だけがRGB(255,128,0)でも、マスターの基準は1になる。
ただし各音の音量には画素支配率が掛かるため、「1画素で音全体が最大音量になる」という意味ではない。

対処候補: 音程参加・退出のヒステリシス、短い解析平滑化、FM量の変化速度制限。
最大値を平均値に変更する場合は既存の音量仕様が変わるため、独立した判断が必要。

## 3. 振幅超過、コンプレッサー、歪み

出力経路は、各音 → master → 24Hzハイパス → compressor → tanh WaveShaper → output gain 0.78。
WaveShaperのカーブは[-1,1]内、入力範囲外は端の値へ制限される。
有限値の正常な処理を前提に、最終デジタルサンプルの振幅上限は約0.78（約-2.16dBFS）。
したがって最終出力の単純なフルスケール超過は第一候補ではない。
端末側の音量増幅・スピーカー歪みや、ソフトクリップ自身の非線形歪みはこの上限では除外できない。

compressorはthreshold -14dB、ratio 10、attack 4ms、release 160ms。
高ゲイン・明暗交互入力では圧縮量が動くため、ポンピングの可能性があるが実測していない。
調査時点のWaveShaperはoversampleがnoneであり、そこで生じた倍音の折り返しも候補だった。
後段の圧縮では既に生じたクリックやFMの折り返しを取り除けない。

対処候補: 処理前後のピーク・RMS、compressor.reductionを測り、圧縮とノイズの時刻を比較する。
WaveShaperだけの2x oversampleは、そのノードで発生する折り返しの比較用であり、上流FMの折り返し対策にはならない。

## 4. FM高音域と指数の定義

実装は`modulator.frequency = carrierFrequency * ratio`、
`modulatorGain.gain = carrierFrequency * fmDepth`。
通常のFM変調指数は周波数偏移を変調周波数で割るため、実効値は`fmDepth / ratio`となる。
彩度・支配率がともに1のとき:

| 音色 | 設定値 | 実効FM指数 |
| --- | ---: | ---: |
| FM 1:1 | 3.0 | 3.0 |
| FM 3:1 | 3.5 | 1.167 |
| FM 3:2 | 2.5 | 1.667 |
| FM SQRT2 | 2.0 | 1.414 |

従来のドキュメントでの「最大変調指数」は、比率が1以外では上記の実効指数と一致しない。
この調査では音色設定を変更していない。

OCT=+2・最高音のキャリアは約3924.45Hz。
FM 3:1の第2上側帯波は3924.45×(1+2×3)=27471.15Hzで、48kHz時のNyquist周波数24kHzを超える。
これは理論上の成分周波数であり、ブラウザ実装の出力スペクトル測定ではない。
初期OCT=0ではこの成分は約6.87kHzなので、高音域条件を確認する必要がある。

対処候補: SINとの比較、OCTを下げた比較、sampleRateに応じたFM深度上限。

## 5. AudioContextとサウンドバッファ

AudioContextはSND開始時に1回作られ、以後再利用される。
発音は12音×2基の常設OscillatorNodeとGainNodeで処理し、発音ごとの生成・破棄はしない。
AudioBufferSourceNode、ScriptProcessor、自前のPCM供給バッファは存在しない。
したがって「アプリが次の音声バッファを供給し忘れる」経路は見つからない。
ブラウザ・OSの音声バッファ不足は別の可能性として残る。

調査時点のContextはオプション未指定で作られ、既定のlatencyHintはinteractiveだった。
balanced/playbackや数値による遅延要求は比較候補だが、実際に採用される遅延は端末次第。
音声の後ろにDelayNodeを足してもレンダリングの処理余裕は増えない。

音量・FM量等の予約時刻はそのフレームのcurrentTimeそのもので、先行予約の余裕はない。
control threadからrendering threadへの操作は非同期なので、重いフレームで複数パラメータが別ブロックに反映される可能性を測る必要がある。
既存17テストは予定値の連続性を確認するが、ブラウザの実レンダリングや遅延配送を検証していない。

対処候補: 実機でsampleRate、baseLatency、outputLatency、Context状態を記録。
小さな先行予約とlatencyHint=balancedをそれぞれ単独で比較し、映像との同期・遅延を評価する。

## 6. 負荷、POLY、ページ状態

通常モードは64×36の画像読取と解析を最大60回/秒行う。
低解像度でもWebGL画像からdrawImage/getImageDataする部分はGPUとの同期コストを測る必要がある。
各フレームで配列等の割り当ても発生する。

数値診断の連続音・3音参加の例では、安定画像60フレームで追加AudioParam呼び出し0、
黒と有色画像を交互にした60フレームで1260回だった。
これはAPI呼び出し回数の比較であり、CPU時間やバッファ不足の証明ではない。
Web Audioは描画を別スレッドで実施するため、メインスレッドの停止を音声途切れと直接同一視できない。

POLYは選択音数を制限するが、全24オシレーターは存続する。
ECOは映像・解析頻度を下げるが、オシレーター数や音声sampleRateは変えない。

ページ非表示ではマスターのフェードなしにsuspendし、復帰時はresumeする。
これはタブ移動・復帰でのクリック候補だが、表示したままの明暗依存ノイズを直接説明しない。
OS割り込み等のContext状態変化を記録する処理も現在はない。

## 対策後の確認優先順位

1. コントラスト最大と明暗差の強い映像で、ENV ON/OFF、SIN/FMを実機比較する。
2. ノイズが残る場合は音声ピーク、圧縮量、更新時刻、解析時間、Context状態を同時記録する。
3. OCTとECOの比較でFM折り返しと処理負荷をさらに切り分ける。
4. 音程参加・退出の揺れが残る場合は、判定ヒステリシスを追加する。

端末・ブラウザ・TONE・ENV・GAIN・OCTの情報を確認して、再現条件を絞る。
